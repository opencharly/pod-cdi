# 2026.323.1302 — fix(pin): compose the driver-free toolkit so the pod base still means "no driver"

## Summary

`pod-cdi` pinned `layer-cdi:v2026.322.1100`, whose `require:` names
`layer-cuda:v2026.321.1520` — a toolkit release that still requires
`layer-nvidia`. A `require:` is target-blind, so the VM **driver** user-space
was composed into every pod that bases on this box and overrides neither layer,
and `layer-nvidia`'s `nvidia-ctk` assertions then ran on an image whose own
composition deletes that binary. That is the contract violation the cutover
exists to remove.

The pin moves to `layer-cdi:v2026.323.0302`, the release whose `require:` names
`layer-cuda:v2026.323.0252`, the toolkit release that dropped
`require: layer-nvidia` (opencharly/layer-cuda#30). The comment beside the pin
records WHY the tag is the contract, so the next reader cannot bump it back
without reading it. One file changed, +9 −1.

This is the fix for **opencharly/pod-cdi#5**, the issue the added comment's own
`#5` reference points at — pre-existing, filed by the session that measured the
chain, not filed by this PR; this PR closes it. Nothing else was filed.

Head `35b13dcd4de81ed7bb123368444bd2ca476ff9a0`.

## How tested

The control is generation: a scratch project imports this box and composes
`pod-cdi` naming NO `layer-cuda` and NO `layer-nvidia`, and the composed
intermediate Containerfile is read directly. Before the bump the base drags the
driver layer in; after it, the same probe emits neither the layer nor the
binary.

Note the scope: the consumer's own `.build/<probe>/Containerfile` only carries
`FROM ${BASE_IMAGE}`, so the layer list lives in the intermediate
`.build/podcdi.pod-cdi/Containerfile`. Grepping the top-level file would read
`0` both before and after — a control that cannot fail — so both files are
counted here.

layer, its package install and its check step, and each moves 1 to 0.
